# Frontend rules (TypeScript / React)

Reviewed by the `frontend-reviewer` agent; structure across layers by the `architecture-reviewer`.

## Scope in this repository

- These are the maintainer's general frontend rules. Metano-specific conventions in `CLAUDE.md` take precedence when they conflict (e.g. JS test layout under `test/`, `#/*` subpath imports, Bun only).
- Generated TypeScript under `targets/js/*/src` (transpiler output) is out of scope: review the transpiler that produced it instead.
- `targets/js/metano-runtime` is a library that mirrors .NET BCL types (`HashSet`, `Enumerable`, `Grouping`, `HashCode`, ...); classes are allowed there when they model a BCL type or a runtime contract consumed by generated code. The layer and signals rules apply to application code (sample consumer apps), not to the runtime.

## Principles

- Always TypeScript. No `any` (use `unknown` and narrow the type).
- Follow SOLID and Clean Code: small functions, one responsibility, dependence on abstractions.
- Semantic, business names. Avoid generic and technical names: `utils`, `helpers`, `common`, `misc`, `data`, `manager`, `handleStuff`.

## Layers

The frontend is layered, but follows Ports & Adapters to control cohesion: each layer only knows the one below it, through that layer's barrel.

| Folder | Role | May depend on |
|---|---|---|
| `components` or `ui` | General-purpose visuals, domain-agnostic. Props and rendering only. One of the two folders per project, never both. | nothing from the application |
| `api` | Backend calls (transport, endpoints, DTOs). No business rules. | — |
| `domain` | Abstractions over domain data, domain services and adapters to `api` (includes the types generated by Metano). | `api` |
| `stores` | Application state and logic. Also the translator/viewmodel between the view model and the domain/api model. | `domain` |
| `screens` | Smart components: screens composed of components, wired to stores and the domain. | `components`, `stores`, `domain` (types) |
| `routes` (or `pages`) | Minimal routing glue: extracts common route parameters and passes them to screens, which ignore routing. | `screens` |

- Group by business inside each layer (e.g. `stores/projects/timeline`), with subfolders when there is specialization.
- Exception: `components`/`ui` is domain-agnostic, so it groups by visual role (e.g. `components/blocks`, `components/sections`, `components/headers`), each category with its own barrel.
- Screens do not call `api` directly; components do not import stores, domain or api.

## Imports and barrels

- Every layer and subfolder exposes a barrel (`index.ts`).
- For another layer, import from the root (alias, e.g. `@/stores/projects`), always through the barrel.
- For the same layer or a direct child, use a relative path.

## No classes: factories

- Do not create classes. Use factories that return objects with fields and closures (`createTimelineStore(deps)`).
- Classes generated by Metano are used as domain data; application code does not declare its own classes.
- Factories are passive: side effects only in attach methods (`attachX`) that return their own cleanup.

## Stores and components

- A component only renders. State and actions come from an object (store/model) created by a factory, pure `@preact/signals-core`, no React.
- A hook memoizes the object's creation; contexts inject the object into the subtree. Global stores are pure signals too.
- A component that reads a signal's `.value` calls `useSignals()` (no signals Babel transform, which is incompatible with the React Compiler).
- `useLiveSignal` only to carry a React value or prop into a signal.
- Do not pass `ref={object.method}`: destructure (`const { attachVideo } = usePlayer()`). Otherwise the React Compiler silently skips the component.
- Components receive the whole `props` object and, if needed, destructure inside the body. Never destructure in the signature, so props can be forwarded (`{...props}`), extended and reused without changing the signature.

```tsx
export function PageSection(props: PageSectionProps) {
  const { title, children } = props;

  return (
    <section>
      <h1>{title}</h1>
      {children}
    </section>
  );
}
```

## Variables

- Declare with `const`, always with an assigned value; `let` only when unavoidable.
- Prefer not to mutate after declaration.
- Conditional initialization goes into a function or factory, not `let` + `if`.

## Formatting and readability

- Every block (`if`, `for`, `while`, `switch`, `try`) is separated by a blank line above and below, except when it is the first or last item in its scope.
- A declaration or call spanning more than one line is also isolated by a blank line above and below, except next to the scope's brace.

```ts
export function createTimelineStore({ project, player }: TimelineStoreDeps) {
  const zoom = signal(1);

  const visibleClips = computed(() =>
    project.clips.filter((clip) => clip.overlaps(player.window.value)),
  );

  return {
    zoom: zoom as ReadonlySignal<number>,
    visibleClips,

    zoomIn() {
      zoom.value = Math.min(zoom.peek() * 2, MAX_ZOOM);
    },
  };
}
```

## Order inside factories and modules

- Top-down reading: constants and signals, derived values (`computed`), inner functions, and finally the returned object.
- Exported types (`ReturnType<typeof createX>`) right after the factory.
